## Incident — I wrote to the live shared Postgres during Run 1

Reporting this first because it is the most important thing I learned.

**What happened.** Run 1 created **8 `party_session` rows in the live shared Postgres
on 127.0.0.1:5433** (session ids visible in the gate log with `created_at`
`2026-09-07T22:56:40` — `22:56:43`). Rows dated 19:53, 21:03 and 21:36 in the same
listing predate my run and are not mine. I have not deleted anything — a delete would
be a second, larger disturbance — so the 8 rows stand.

**Why the pre-flight did not stop it.** Two compounding reasons:

1. The four writers — `party-cli`, `party-e2e`, `party-decisions-cli`,
   `party-decisions-e2e` — contain **no dial primitive at all**. They shell out to
   `gsd-tools.cjs party`, which reaches `services/party_session.py`, which calls
   `pg_store._get_conn()`. My sweep looked for connections *in test files*. Three
   call-frames of indirection made every one of them invisible to it.
2. `services/pg_store.py:114` declares
   `DEFAULT_PG_URL = "postgresql://gsd:gsd@127.0.0.1:5433/gsd_amauta"`, resolved as
   `self.dsn = dsn or os.environ.get("GSD_POSTGRES_URL", DEFAULT_PG_URL)`.
   I found `GSD_POSTGRES_URL` set to the live instance in the inherited shell and
   `env -u`'d it, reasoning that CI has it unset. **Unsetting it made things worse,
   not better**: it removed the only override and handed the connection to a hardcoded
   pointer at the live database.

**The generalisable lesson.** `env -u` on a variable whose consumer has a hardcoded
live default is not a safety control — it is the removal of one. The control is to
*set* the variable to a dead endpoint. Runs 2 and 3 used
`GSD_POSTGRES_URL=postgresql://nobody:nobody@127.0.0.1:1/nodb` and I verified the
resolved dsn by importing the module before running. Nothing was written in Runs 2 or 3.

Daemon 18799, RLM 18798 and Redis 6379 were not written to in any run. No service was
restarted, killed or reconfigured; no `docker compose`, no `pkill`.

## Clusters — by root cause

### 1. The agent roster grew from 11/16/17 to 35; the tests hardcode the old counts — 28 failures
`23-prefix-stability` (7) · `security-infrastructure` (6) · `comprehensive-e2e` (4) ·
`agent-compiler-hydrate` (4) · `06-05-capability-index`, `agent-md-to-yaml`,
`codex-config`, `33-pact-contracts`, `pipeline-offline`, `research-chain`,
`rlm-workflow-spec` (1 each).

Evidence is in the assertion text: `Expected 11 gsd-*.md files in agents/, found 35`,
`compile() must produce 17 outputs. Got: 35`, `Expected 16 agents, got 19`,
`Expected 3 pact files, found 5`, `Expected 7 UP migrations, got 28`. A second,
subtler half of the same cause: contracts that every agent must satisfy were never
applied to the agents added since — `gsd-architect.md` has no `<role>`/`<patterns>`
in its stable prefix, `gsd-auditor-models.md` has 5 `CACHE_BREAKPOINT` markers instead
of 1 and a 10.5% stable prefix.

**Category: (a) genuine drift.** The repository grew; the assertions were pinned to a
census taken at a phase boundary and never re-pinned. This is the single largest cause
and it is the one to fix first — it also detonates cluster 3.

### 2. `process.exit()` truncates stdout at the 8 KB pipe buffer — 10 failures
`34-security-pipeline` (7) + the cascade in `35-`, `36-`, `37-` (1 each).

Every one reports `Unterminated string in JSON at position 8192`. `8192` is the pipe
buffer, not a `maxBuffer` (none is set). `scripts/rule-of-two-audit.cjs` ends with
`console.log(json)` immediately followed by `process.exit(0)`. When stdout is a pipe —
which is exactly what `spawnSync` gives it — writes are asynchronous and `process.exit`
terminates the process before the pipe drains. Run by hand with stdout redirected to a
file the same script emits **19,328 bytes** and rc=0, because file writes are
synchronous on POSIX. The script "works" everywhere except where the test runs it.

**It is caused by cluster 1.** The report is ~552 bytes per agent. At 35 agents it is
19 KB and truncates; at the 11 agents the suite was written for it was ~6 KB and fit
under the buffer. Growing the roster pushed a latent bug over a threshold.
`35-`/`36-`/`37-` fail only because each shells out to the previous test file and
asserts `exit 0` — three failures carrying no information of their own.

**Category: (c) always wrong, newly visible.** This is the same family as the
`cmd | tail` rule in the harness memory: a result read through a pipe. The rule needs
widening from exit codes to output.

### 3. Canary freeze assertions against a repo that moved on — 13 failures
`phase-52-canary` (4) · `party-canary`, `party-decisions-canary`, `phase-53-canary` (3 each).

All say some variant of `must be UNMODIFIED since <base>`. All four base SHAs resolve
(`3889ff38`, `dd404b7e`, `21438ae4`, `32fbdc31`) — no orphaned SHA here. The freeze is
simply long past. Measured directly with `git diff <base> master`: **`master` is
already 8,173 – 9,449 lines divergent from every one of the four bases, across 29 files,
including every protected path.**

**Category: (c) a test that was always going to fail once the next phase landed.**
A freeze nobody lifted. These are historical assertions, not regressions.

### 4. `services/amauta-mcp.py` was rewritten; the test asserts the old source shape — 10 failures

## Do the failures also fail on `master`? — Yes. 98 of 108.

Never answered before, so here is the method as well as the answer.

**Method.** `git archive master | tar -x` into a scratch directory — no checkout, no
stash, nothing written to the repo and the dirty working tree left alone — then Runs 2
and 3 back to back under *identical* environment, node v22.14.0, the same 22-file
exclusion, differing only in the tree. Failures compared by `(file, test name)`.

**Result.** 85 of 108 working-tree failures fail byte-for-byte identically on `master`.

The 23 that differed break down further:

- **13 canary failures** are an artefact of my own method, not a real difference: a
  `git archive` tree has no `.git`, so the git-based canaries error at load rather than
  running. Answered separately and directly with `git diff <base> master` — `master` is
  8,000+ lines past every base, so **these fail on `master` too**. 85 + 13 = **98**.
- **10 are genuinely worktree-only**: the 8 `complexity-scorer` failures (cluster 6) and
  the 2 distill failures (cluster 9). Both trace to uncommitted changes on
  `fix/memory-distill-containment`.

Two failures go the other way, failing on `master` and passing in the working tree —
`agents-compile-claude-target-byte-match` (whose name already says "all 35 agents") and
a `gitleaks`-conditional check.

**So: the suite is broken on the default branch, independent of any branch under
development.** 91% of what fails is pre-existing. The brief's instruction to leave
`fix/ci-branch-filter-master` unmerged is well founded, and for a sharper reason than
stated — that branch would turn CI on for the first time (its commit message notes the
Actions API reports `total_count 0` for `test.yml` over the repo's life) and the first
green would be 90 failures on `master` itself.

3. `tests/14-plan-to-tasks.integration.test.cjs` — **spawns its own `amauta-daemon.py run`**; risks binding a port the live daemon already holds
4. `tests/27-02-ingestion.test.cjs` — **POSTs `/reindex` to the live RLM 18798**; the worst of the set, it does not read the RLM, it drives a reindex
5. `tests/27-03-search-pipeline.test.cjs` — RLM 18798, two dials

7. `tests/complex-integration.test.cjs` — python exec against the daemon library

9. `tests/step-orchestrator.test.cjs` — `psycopg2.connect` to 5433, two sites
10. `tests/test-init-flow.test.cjs` — python infra-detect probing PG and RLM

**But the 22/12/10 split is the wrong frame, and this is the finding that matters for
the follow-up task.** The 12 "guarded" files are guarded the *wrong way round*. Their
guard reads *skip when the daemon is unreachable* — an **availability** guard that
protects the test from a missing service. It is not a **containment** guard, and it says
nothing about what happens when the service *is* there. On this machine, where all four
services are live, every one of those 12 files drives them. `step-handoff-daemon.test.cjs`
is a good example and the one the brief named: it does probe `/health` and set a
`SKIP_REASON`, and it is nonetheless dialling 18799 to find that out.

Of all 210 files, exactly one is a real containment guard:
`tests/85-01-memsafe-containment.test.cjs`, which holds `REAL_DAEMON_PORT = 18799` in
order to `assert.notStrictEqual` against it.

And the enumeration is incomplete by construction. Four more files —
`party-cli`, `party-e2e`, `party-decisions-cli`, `party-decisions-e2e` — wrote to the
live Postgres in Run 1 while containing **no dial primitive of any kind**, reaching it
three call-frames deep through `gsd-tools.cjs party` → `party_session.py` →
`pg_store._get_conn()`. No file-level sweep of the test directory can find those. At
least 26 files touch shared services, and the honest answer is that the file list is a
lower bound.

**Recommendation for the separate workflow task:** do not build it on a file list.
Build it on the environment — set every service endpoint to a dead address by default
and require a test to opt in — and fix `services/pg_store.py:114` so an unset
`GSD_POSTGRES_URL` fails closed instead of defaulting to the live database.

## What in this brief was wrong

Seven things. The first was load-bearing; the last was the expensive one.

1. **`GSD_SKIP_SERVICE_TESTS` does not exist.** The brief says to set it, says "the
   runner honours it", and says the unmerged branch adds the guard to
   `scripts/run-tests.cjs`. None of that is true. The variable appears nowhere in the
   repository — not in `scripts/run-tests.cjs`, not in `package.json`, not in any
   workflow, not on any ref (`git grep` across all reachable commits: zero hits).
   `fix/ci-branch-filter-master` is a **single commit, `2ea183f`, touching one file,
   `.github/workflows/test.yml`, +2 lines** — it adds `master` to the two branch
   filters and nothing else. Had the brief not also said "confirm by reading
   `scripts/run-tests.cjs` that it actually excludes them before you rely on it", this
   lane would have run all 210 files against four live services believing itself
   guarded. The instruction to verify was worth more than the fact it was verifying.

2. **The control model itself was wrong, and it cost a live write.** The brief frames
   containment as a per-file property — "23 test files drive those live services" —
   which invites a file-exclusion control. Containment is not a per-file property here.
   Four `party-*` files reach the shared Postgres with no dial primitive anywhere in
   them, and `services/pg_store.py:114` hardcodes the live DSN as the fallback for an
   unset `GSD_POSTGRES_URL`. Following the file model, I excluded 22 files, unset the
   variable to match CI, and wrote 8 rows to the live database. Unsetting was not
   neutral: it deleted the only override and deferred to a hardcoded pointer at the
   live instance.

3. **"93 assertion failures, 66 distinct top-level" does not reproduce.** Complete runs
   on node v22.14.0 give **108** on the working tree and **90** on `master`. The
   failures span **34** distinct files, not 66. The brief's inference from the ratio —
   few root causes, cluster first — was nonetheless correct and was the right
   instruction.

4. **"`CACHE-01`/`CACHE-03` prefix stability" is a phantom cluster** — two unrelated
   things fused into one name. No `CACHE-01` or `CACHE-03` label exists in the suite.
   The nearest are `ECACHE-01`/`ECACHE-03` in `tests/04-03-embed-cache.test.cjs`, about
   the *embedding cache* — and that file **passes**, in all three runs. Prefix stability
   is `tests/23-prefix-stability.test.cjs`, which does fail (7), under no CACHE label at
   all. Chasing "CACHE-01" would have led to a green file.

5. **The guard counts are wrong, and so is their polarity.** 22 files dial, not 23;
   12 guarded and 10 unguarded, not 12 and 11. More importantly the brief treats
   "guarded" as meaning safe. It means the opposite of what is needed here: those guards
   skip when a service is *absent*, so they drive it whenever it is *present*. Exactly
   one file in the repository is a containment guard.

6. **"The 179 clean files."** There are 210 test files in the working tree and 202 on
   `master`; my non-service run set is 188. 179 matches no inventory I can find.

7. **The RLM pid is 41885, not ~81378** — 81378 does not exist. The daemon pid 81360 was
   correct. Also worth flagging while looking: **two things listen on 6379** — a native
   `redis-server` (pid 1115) on 127.0.0.1 and Docker (pid 54005) on the IPv6 wildcard —
   so "Redis 6379" is not one service, and which one a client reaches depends on address
   family. And `.github/workflows/test.yml` declares `node-version: [18, 20, 22]` while
   `package.json` sets `"engines": {"node": ">=20.0.0"}`: the matrix tests a version the
   package declares unsupported.
