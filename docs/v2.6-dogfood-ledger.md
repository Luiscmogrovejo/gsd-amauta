# v2.6 Dogfood Ledger

This document is the published, human-readable record of observed instances
of the divergence protocol (shipped in Phase 13.1) and the orchestrator
hardening measures around it firing in real v2.6 work. It is a transcription
of memory entries maintained at
`~/.claude/projects/-Users-luismogrovejo-Code-gsd-amauta/memory/`. Memory
remains the source of truth; this file is a derived artifact so that future
readers can find the ledger without knowing where the memory store lives.

## What this is

This ledger documents observed instances of the divergence protocol and
orchestrator hardening measures introduced in v2.6 (Phase 13.1) firing in
real work. Each entry represents a moment where an agent — executor,
orchestrator, or validator — recognized a scope boundary, resisted a
rationalization, or surfaced a plan-vs-reality mismatch instead of silently
absorbing it.

The entries are ordered by "recursive depth" — how many layers of
self-reference the discipline penetrated. Depth 0 is an executor applying
the protocol to external work. Higher depths are agents applying the
protocol to the protocol's own artifacts, to the process of maintaining
those artifacts, or to the tooling that audits the protocol itself.

The gap at depth 3 is intentional. It has not yet been observed in the
v2.6 milestone. The ledger does not renumber to hide gaps — a ledger that
rearranges itself to appear complete cannot be trusted for provenance.

The negative counterpart against which every entry is implicitly measured
is the Phase 13 silent scope expansion incident
(`project_phase13_incident.md`). That incident is not itself a ledger entry
because it preceded the protocol; it is the failure mode every entry in
this table documents resistance to.

## Expected shape of depth-3

Depth 3 would be **sub-task-level recursion within an executor's own
work**: an executor, while implementing a task, recognizing that a
specific sub-step of their implementation is exhibiting the same
scope-creep or rationalization pattern that the divergence protocol was
designed to catch — and naming it at that granularity rather than at the
task level.

Where depth 2 is "executor resists temptation at task boundary" and
depth 4 is "orchestrator resists temptation at process boundary," depth 3
would be the executor catching the pattern within a single function,
test, or file edit — below the task level but above the character level.
A concrete example might be: an agent mid-execution applying the protocol
to a helper function that applies the protocol to its own output.

What "not yet observed" means for a ledger driven by this protocol is
itself an open question. Two possibilities:

1. **The depth does not exist in practice.** The protocol's decision
   tree operates at natural scope boundaries (task, plan, wave, phase,
   workflow, milestone). Intra-task sub-step recursion may simply not be
   a boundary agents attend to. In that case depth 3 will remain empty
   forever and the ledger's gap is a correct observation about where the
   discipline lives.

2. **The depth has been silently catching things that never get
   formalized.** Sub-task-level resistance may be happening regularly
   without being written up, because the granularity feels too small to
   warrant a memory entry. In that case depth 3 is a reporting gap in
   the ledger itself: agents are doing the work, but the meta-layer
   isn't recording it.

The ledger does not resolve which of these is true. It preserves the gap
honestly so that future phases can test either hypothesis. This gap will
close naturally (if at all) as more v2.6+ work is executed. **It should
not be manufactured.**

## Limitations of this ledger

### Schema-orphaned depths

The Wave 1 verification script (`scripts/verify-v26.cjs`) was authored
before depths 8 and 9 existed. Its JSON schema (`Q7` in
`15-CONTEXT.md`) has a `dogfood_ledger_depths_captured` field that the
Wave 2 audit populated as `[0, 1, 2, 4, 5, 6, 7]` — the depths the script
knew about at authoring time. Depths 8 and 9 are **not** encoded anywhere
in `15-AUDIT-REPORT.json`.

This has a concrete consequence: future automated consumers of the audit
JSON will not see two of the most important Phase 15 findings. Depth 8
(the init-resolver bug recurring across workflow surfaces) and depth 9
(the four resisted patches to the audit script itself, which are the
meta-proof that Phase 15's observational discipline held) are captured
**only in this ledger, in memory, and in Wave 2's `15-02-SUMMARY.md`.**

## How this ledger is maintained

1. **When to add an entry:** Any time an agent (executor, orchestrator,
   checker, validator, or auditor) recognizes and names a rationalization
   or scope boundary during real work. The key signal is: the agent
   could have silently acted, but instead surfaced the observation.

2. **What to record:** Phase, actor role, artifact being worked on, the
   rationalization that was named (quoted where possible), and the
   outcome. Include a literal quote from the memory entry in the detail
   section so future readers can see the exact articulation, not a
   paraphrase.

3. **Depth assignment:** Depth reflects how many layers of self-reference
   the observation penetrated:
   - **Depth 0:** Protocol applied to external work product
   - **Depth 1:** Protocol applied to the protocol's own artifacts
     during their creation
   - **Depth 2:** Protocol applied to a temptation during protocol
     artifact work at a hard ceiling
   - **Depth 3:** Protocol applied within a single implementation step
     (not yet observed)
   - **Depth 4+:** Protocol applied to process/workflow artifacts that
     govern protocol application (paperwork, discuss-phase init,
     execute-phase init, audit-script execution, etc.)

4. **Source linking:** Every entry must cite the memory file where the
   observation was first recorded, with path and at least one literal
   quote. If no memory file exists, create one before adding the ledger
   entry.

5. **No renumbering:** Gaps in depth are findings, not errors. Do not
   renumber depths to close gaps. The depth-3 gap is preserved honestly
   across all future revisions of this ledger.

6. **Phase 13 incident as negative anchor:** The Phase 13 silent scope
   expansion incident (`project_phase13_incident.md`) is the failure mode
   this entire ledger documents resistance to. It is NOT an entry in the
   ledger (it preceded the protocol), but every entry implicitly
   references it as "this is what we would have done before."

7. **Do not edit historical entries for stylistic consistency.** Each
   entry preserves the voice and articulation of its memory source.
   Normalizing the language would erase the distinct rationalizations
   (for example, "the helper is useless if nothing consumes it" vs
   "while I'm here" vs "the report says X and reality is Y") that are
   the grep-worthy evidence future research can match against.
