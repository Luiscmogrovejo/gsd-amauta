## Phase Details

### Phase 11: Context Engine Activation
**Goal:** RLM enrichment works on every RPETD phase for every task, querying the project's own codebase via direct HTTP with BM25 scoring
**Dependencies:** None (standalone)
**Success Criteria:**
1. `_rpetd_phase_enrich()` calls `_rlm_query()` on all 5 phases without `if doc_path:` gate
2. `_rlm_query()` queries project CWD via HTTP GET to localhost:18798 (no subprocess)
3. `_enrich_task_context()` (Layer 1) includes 2 RLM queries for relevant code at claim-time
4. rlm-service.py uses BM25 formula with document length normalization
5. Tokenizer splits camelCase (`getUserProfile` → 3 tokens) and snake_case (`get_user_profile` → 3 tokens)
6. Full RPETD cycle adds ≤1.5s from RLM (vs ~0s currently since it's dead)
7. All existing tests pass, new tests cover HTTP path and BM25

**Key files:**
- `amauta.py` — `_rlm_query()`, `_rpetd_phase_enrich()`, `_enrich_task_context()`
- `services/rlm-service.py` — scoring, tokenizer, ChunkCache

**Research:** `.planning/research/RLM-INTEGRATION.md`

### Phase 12: Semantic Memory Pipeline
**Goal:** Memory queries use vector similarity instead of LIKE matching, all writes generate embeddings, research chain fires automatically in R-phase, SKB stays clean
**Dependencies:** None (standalone, but benefits from Phase 11 RLM being active)
**Success Criteria:**
1. R-phase calls daemon `/api/memory/semantic-search` instead of `_mem_pg_search()` LIKE query
2. All `_mem_log_event()` calls route through daemon HTTP POST `/api/memory/store` for auto-embedding
3. E-phase enrichment queries memory for `fail|error|blocker` on same domain (top 3)
4. T-phase enrichment queries memory for `test|validation|criteria` on same domain (top 3)
5. R-phase enrichment auto-invokes research chain (gsd-research.cjs) when PG memory returns <2 results
6. `_skb_promote()` checks Jaccard similarity >0.7 against existing entries before inserting
7. `_auto_write_learning()` stores full phase content without double-truncation
8. All existing tests pass, new tests cover semantic search path and dedup

**Key files:**
- `amauta.py` — `_mem_pg_search()`, `_mem_log_event()`, `_mem_pg_add()`, `_rpetd_phase_enrich()`, `_skb_promote()`, `_auto_write_learning()`
- `services/pg_store.py` — `memory_semantic_search()`, `memory_store_with_embedding()`
- `services/amauta-daemon.py` — memory routes
- `get-shit-done/bin/gsd-research.cjs` — research chain cascade

**Research:** `.planning/research/PGVECTOR-SEMANTIC.md`

### Phase 13: Validation Hardening
**Goal:** Validation gates cannot be bypassed without explicit justification, evidence patterns catch real issues, audit trail captures all overrides
**Dependencies:** None (standalone)
**Success Criteria:**
1. `--force` flag on `validate` command replaced with `--force-reason "text"` (non-empty required)
2. `_has_test_evidence()` removes 100-char proxy fallback; requires structured signal or `--test-exempt` flag
3. `_has_explicit_learning_written()` requires >100 chars with structured keyword
4. `cmd_validate()` blocks when `claimed_by == validated_by` unless `--force-reason` provided
5. `cmd_status()` for failed/deferred requires `--note` argument (non-empty)
6. `cmd_status()` with `--force` records `forced: true` in audit log metadata
7. All existing tests updated for new flag names, new tests cover hardened gates
8. Existing `--force` on `add` and `skb` commands unchanged

**Key files:**
- `amauta.py` — `cmd_validate()`, `cmd_status()`, `_has_test_evidence()`, `_has_explicit_learning_written()`, argparse definitions
- `services/amauta-daemon.py` — audit log writes

**Research:** `.planning/research/RPETD-ENFORCEMENT.md`

### Phase 14: Pipeline Integration
**Goal:** All systems visible and connected — MCP registered, performance influences routing, failures surface, health dashboard works
**Dependencies:** Phases 11-13 (builds on activated systems)
**Success Criteria:**
1. `bin/install.js` registers MCP server in `~/.claude/settings.json` under `mcpServers`
2. Execute-phase workflow reads agent performance data and uses pass rate as tiebreaker when multiple executors qualify
3. Daemon dual-write failures append `[PG_SYNC_WARN]` to task mutation stdout (visible to agent)
4. `amauta status` shows: daemon health, RLM health + cache stats, PG connection, embedding coverage %, task counts, SKB size, agent performance summary
5. All existing tests pass, new tests cover MCP registration and status output

**Key files:**
- `bin/install.js` — MCP registration
- `commands/amauta/execute-phase.md` or workflow — routing logic
- `services/amauta-daemon.py` — dual-write error surfacing
- `amauta.py` — new `cmd_status_dashboard()` or enhanced existing `status` subcommand

**Research:** `.planning/research/PIPELINE-WIRING.md`
