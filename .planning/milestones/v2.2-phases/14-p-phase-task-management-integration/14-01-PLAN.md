# Plan 14-01 — Protocol & Schema Foundation

## Goal

Lay the foundation that all subsequent Phase 14 plans depend on: bump
divergence-protocol.md to v1.1.0 with both new enum values
(`agent_assignment_conflict`, `plan_amauta_drift`), create the
`plan-task-xml-schema.md` reference file locking the `<story>` + `<task>`
schema, and add the 3-5 line runtime Read pointer in gsd-planner.md.

## Scope

- `divergence-protocol.md` version bump 1.0.0 -> 1.1.0 (single atomic edit with
  both new enum values).
- New reference file `get-shit-done/references/plan-task-xml-schema.md` locking
  the `<story>` + `<task>` + `<files_expected>` + `<depends_on>` schema.
- `agents/gsd-planner.md` `<planning_protocol>` section gains ~4 lines pointing
  at `plan-task-xml-schema.md` via runtime Read pattern.

## Must-Haves

- [ ] `divergence-protocol.md` version field is `"1.1.0"`.
- [ ] `divergence_type` enum line contains all 7 values including
      `agent_assignment_conflict` and `plan_amauta_drift`.
- [ ] `plan-task-xml-schema.md` exists with mandatory `<story>` block schema
      and mandatory `<task>` child-element schema (child-element style, not
      attribute style).
- [ ] `gsd-planner.md` contains a Read instruction pointing at
      `plan-task-xml-schema.md`.
- [ ] `gsd-planner.md` line count does not exceed 204 (current 200 + 4 lines).

    **Part A: Create `get-shit-done/references/plan-task-xml-schema.md`**

    Frontmatter:
    ```
    version: "1.0.0"
    reference_type: runtime-read
    scope: gsd-planner
    ```

    Content must define and lock the following schema elements:

    1. **`<story>` block (MANDATORY, top-level sibling to `<task>`):**
       - `<title>` — story title (becomes `amauta add story` title)
       - `<success_criteria>` — Given/When/Then format; inherited by child tasks via `_inherit_parent_spec` at claim time
       - `<doc_refs>` — list of canonical reference files (dash-prefixed)

    2. **`<task>` block (child-element style, NOT attribute style):**
       - `id` attribute on `<task>` element: `"{plan_id}-{NN}"` format (e.g. `"14-01-01"`)
       - `<title>` — task title
       - `<agent>` — executor agent short name (no `gsd-` prefix): `executor-backend`, `executor-frontend`, `executor-infra`, `executor-general`
       - `<depends_on>` — JSON array of task IDs: `[]` for no deps, `["14-01-01"]` for explicit dep. Dependencies are EXPLICIT ONLY, no implicit N+1 ordering. Tasks without `<depends_on>` entries are parallel-eligible by default.
       - `<read_first>` — files executor must read before working (dash-prefixed list)
       - `<action>` — concrete instructions with exact values
       - `<acceptance_criteria>` — grep-verifiable conditions (dash-prefixed list)
       - `<files_expected>` — MANDATORY manifest block with `modify:`, `create:`, `delete:` YAML sublists

    3. **Validation rules (documented in the reference file itself):**
       - A PLAN.md without a `<story>` block is rejected as malformed
       - Every `<task>` must have a `<files_expected>` block (HARDEN-01 mandate)
       - Every `<task>` must have a non-empty `<agent>` field
       - `<depends_on>` values must reference IDs within the same plan
       - Maximum 10 `<task>` elements per plan

    4. **Phase cutoff note:** Schema applies to phases >= 14. Phases 9-13 are grandfathered — their PLAN.md files are NOT parsed for registration.

    Include a complete example block showing one `<story>` and two `<task>` elements (one with a dependency on the other), using Phase 14 naming conventions.
