    ## Expected shape of depth-3

    Depth 3 would be **sub-task-level recursion within an executor's own work**:
    an executor, while implementing a task, recognizing that a specific sub-step
    of their implementation is exhibiting the same scope-creep or rationalization
    pattern that the divergence protocol was designed to catch --- and naming it
    at that granularity rather than at the task level.

    Where depth 2 is "executor resists temptation at task boundary" and depth 4
    is "orchestrator resists temptation at process boundary," depth 3 would be
    the executor catching the pattern within a single function, test, or file
    edit --- below the task level but above the character level.

    This gap will close naturally as more v2.6 work is executed. It should not
    be manufactured.

    ## How this ledger is maintained

    1. **When to add an entry:** Any time an agent (executor, orchestrator,
       checker, validator) recognizes and names a rationalization or scope
       boundary during real work. The key signal is: the agent could have
       silently acted, but instead surfaced the observation.

    2. **What to record:** Phase, actor role, artifact being worked on, the
       rationalization that was named (quoted if possible), and the outcome.

    3. **Depth assignment:** Depth reflects how many layers of self-reference
       the observation penetrated:
       - Depth 0: Protocol applied to external work product
       - Depth 1: Protocol applied to the protocol's own artifacts
       - Depth 2: Protocol applied to a temptation during protocol artifact work
       - Depth 3: Protocol applied within a single implementation step (not yet observed)
       - Depth 4+: Protocol applied to process/workflow artifacts that govern protocol application

    4. **Source linking:** Every entry must cite the memory file where the
       observation was first recorded. If no memory file exists, create one
       before adding the ledger entry.

    5. **No renumbering:** Gaps in depth are findings, not errors. Do not
       renumber depths to close gaps.

    6. **Phase 13 incident as negative anchor:** The Phase 13 silent scope
       expansion incident (`project_phase13_incident.md`) is the failure mode
       this entire ledger documents resistance to. It is NOT an entry in the
       ledger (it preceded the protocol), but every entry implicitly references
       it as "this is what we would have done before."
