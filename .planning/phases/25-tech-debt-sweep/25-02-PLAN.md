# Plan 25-02: Wrapper Parity + routeExecutor Specificity

## Objective

Close DEBT-03 (amauta.cjs wrapper parity) and DEBT-04 (routeExecutor specificity-wins determinism).

### DEBT-03 Analysis

The `get-shit-done/bin/amauta.cjs` wrapper is now a 1-line delegation to `gsd-amauta.cjs`:
```js
require(require('path').join(__dirname, 'gsd-amauta.cjs'));
```

The v2.7 finding ("amauta.cjs wrapper routes through /api/exec and rejects CLI commands") appears to have been resolved at some point between v2.7 and v2.8, since the current wrapper is a straight require. The `bin/cli.cjs` wrapper (the `npx gsd-amauta` entry point) also delegates to `gsd-amauta.cjs` for all non-init/non-status-system commands.

DEBT-03 requires a parity test confirming both wrappers produce identical output for representative commands, ensuring the fix is locked with a regression test.

### DEBT-04 Analysis

`routeExecutor` currently uses hardcoded priority ordering (frontend > infra > backend > general). When multiple agents match the same file, the hardcoded order determines which wins. This is deterministic but not specificity-based.

The requirement says: "given two agents matching the same file, the one with higher specificity wins (longer glob)." For example, if executor-infra has `k8s/*` and executor-backend has `*.yaml`, a file like `k8s/deployment.yaml` should route to infra (more specific) regardless of the iteration order.

The fix: after collecting all agent matches, sort by pattern specificity (longest matching pattern wins) before selecting the winner. Fall back to the existing priority order as a tiebreaker.

## must_haves

- amauta.cjs and gsd-amauta.cjs produce identical output for list and board commands
- routeExecutor selects the agent with the longest matching pattern when multiple agents match
- Regression tests for both DEBT-03 and DEBT-04

  <action>
    Modify routeExecutor in gsd-tools.cjs to use specificity-based selection instead of hardcoded priority order.

    Current approach: iterate agents in hardcoded order [frontend, infra, backend], return first match.
    New approach:
    1. Collect ALL matching (agent, pattern) pairs across all agents.
    2. If zero matches, return 'executor-general'.
    3. If one match, return that agent.
    4. If multiple matches, sort by specificity score:
       - Exact match (no wildcard): score = pattern.length + 1000
       - Directory prefix match (dir/*): score = pattern.length + 100
       - Filename prefix match (Dockerfile*): score = pattern.length + 50
       - Extension match (*.tsx): score = pattern.length
    5. Highest score wins. On tie, use the existing priority order as tiebreaker:
       frontend (priority 0) > infra (priority 1) > backend (priority 2) > general (priority 3).

    This preserves all existing routing behavior (*.tsx still beats *.ts because frontend patterns are checked AND .tsx is more specific than .ts by length). The key change is that k8s/deployment.yaml routes to infra (k8s/* = length 4 + 100 = 104) not backend (*.yaml = length 6), because directory prefix has higher specificity class than extension match.

    IMPORTANT: All 27 existing tests in 06-02-routing-accuracy.test.cjs MUST still pass. The specificity logic must be backward compatible with the existing hardcoded priority for all current patterns.
  </action>

    - grep -c 'specificity' get-shit-done/bin/gsd-tools.cjs returns >= 1 (specificity logic present)
    - The routeExecutor function collects all matches before selecting, not short-circuiting on first match
